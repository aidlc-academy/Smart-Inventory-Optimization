# Smart Inventory Optimization MVP — Full-stack implementation

The change delivers a complete React+TypeScript+Vite frontend, Node.js+Express backend, and SQLite database for a formula-based inventory management app. Backend formula functions, product CRUD, transactional sales/restock routes, a dashboard aggregation endpoint, and demo-seeding all land together with FEAT-001; the frontend with typed API client, formula utilities, dashboard page, product detail page, and all shared components lands in FEAT-002. All 43 backend Jest tests and 34 frontend Vitest tests pass. The implementation is student-scoped: straightforward TypeScript, no framework overreach, pure functions for calculations.

**Watch for:** One confirmed discrepancy — the error message in AC-05-4 of requirements.md says `"current stock: N"` but both the implementation and design.md say `"current: N"`. The frontend ProductDetailPage re-computes demand metrics from the locally-fetched 30-day sales list, but the backend GET /api/v1/products/:id/sales only returns the last 30 days, so the frontend ADD_7 figure can silently diverge from the dashboard ADD_7 if a product has no sales in the last 30 days but has older records that the backend's dashboard query also wouldn't reach anyway — this is consistent but worth noting. The `calcTrendWarning(add3, add7)` with `add7=0, add3>0` returns `true` (confirmed correct per formula), but the frontend inventory test suite doesn't cover this edge case.

**Verdict**: APPROVED

## High-level view

All eight formula functions (`calcADD7`, `calcADD3`, `calcROP`, `calcStockCoverage`, `calcTargetStock`, `calcSuggestedOrderQty`, `calcStatus`, `calcTrendWarning`) are implemented identically in both backend and frontend, matching `calculation-rules.md` exactly. The `Math.ceil` on ROP and suggested order quantity, the null-return on zero demand for coverage, and the strict `>` boundary on trend warning all match the spec.

Sales and restock mutations both use `db.transaction()`. The negative-stock guard reads `current_stock` inside the transaction and compares `currentStock - delta < 0` before mutating, preventing the race-condition window a pre-transaction read would leave. Stock movement quantities use signed convention (negative for sales, positive for restocks), which the frontend renders with `+/-` prefix colouring.

The dashboard endpoint sorts Reorder now → Watch → Healthy → alphabetical via a `statusPriority` map before returning, satisfying US-09. The `FormulaTrace` component appears on ADD_7, ADD_3, and ROP columns; the `FormulaDrawer` covers the full three-step Suggested Order Quantity derivation including "User-set assumption" labels on safety stock and target coverage days.

The demo seed generates Coffee at stock=18 with a deliberate sales split (days -6..-4 at 3/day, days -3..0 at 6/day) inside the ADD_7 window, producing ADD_7≈4.71, ADD_3=6.0, and a trendWarning. ROP=29 with stock=18 gives "Reorder now". Seed values for Coffee (18), Flour (120), and Oil (40) match the plan. All three products carry `is_sample=1` and the frontend renders "(Sample)" tags.

There is one confirmed wording divergence: requirements.md AC-05-4 specifies `"current stock: N"` in the error message, but the implementation emits `"current: N"` — matching design.md and the FEAT-001 spec. Both documents agree with the implementation, so this is a stale phrase in requirements.md rather than a code defect, but a reviewer checking AC-05-4 verbatim will see a mismatch.

### Formula correctness — confirmed match

Every formula function matches `calculation-rules.md` §1 exactly:

- `calcADD7` and `calcADD3` divide by the fixed denominator (7 or 3) regardless of how many days have data — correct per the spec's stability rationale.
- `calcROP` applies `Math.ceil` to the full expression `add7 * leadTimeDays + safetyStock`, not just the product — confirmed correct.
- `calcStockCoverage` returns `null` (not `0`, not `Infinity`) when `add7 === 0`.
- `calcSuggestedOrderQty` applies `Math.ceil` to `targetStock` before subtracting `currentStock`, not after — correct per spec.
- `calcStatus` uses `currentStock <= rop * 1.25` for the Watch upper boundary, meaning `rop * 1.25` itself falls in "Watch" not "Healthy". The backend test `calcStatus(12.5, 10)` → `'Watch'` and the frontend test `calcStatus(25, 20)` → `'Watch'` both confirm this.
- `calcTrendWarning` uses strict `>`, so `add3 === add7 * 1.20` correctly returns `false`.

The frontend `calcROP(5, 0, 8)` test checks `leadTime=0` returning `safetyStock=8`, which the backend doesn't have but is correct behavior.

### Transaction safety and negative-stock prevention — confirmed

`POST /api/v1/products/:id/sales` wraps all six steps in `db.transaction()`. The guard at step 3 re-reads `current_stock` from the database inside the transaction (not from the pre-flight check), eliminating the TOCTOU gap. The delta calculation `newQty - oldQty` correctly handles upsert cases — reducing a sale entry from 10 to 3 produces `delta = -7`, which passes the `currentStock - (-7) >= 0` check and increases stock by 7. The test "updating to fewer units than before increases stock" covers this path.

`POST /api/v1/products/:id/restock` wraps its two steps in `db.transaction()`. No negative-stock risk for restocks (quantity is validated `>= 1`).

### Error message discrepancy — confirmed

requirements.md AC-05-4: `"Cannot record sale: would reduce stock below zero (current stock: N, requested: M)"`

Implementation (`sales.ts` line 72–73): `` `Cannot record sale: would reduce stock below zero (current: ${currentStock}, requested: ${newQty})` ``

design.md and FEAT-001 spec both use `"current: N"`. The backend test (`sales.test.ts`) asserts `toContain('current: 5')` and passes. The mismatch is documentation-only, but a reviewer running AC-05-4 verbatim will fail the acceptance check. One of the two must be updated.

### No AI/ML language — confirmed clean

`grep` across all `.ts` and `.tsx` files under `smart-inventory-optimization/` finds zero occurrences of `AI`, `ML`, `machine learning`, `predict`, `forecast`, or `neural` in user-facing strings or rendered UI. The two matches returned are JSDoc comments documenting the prohibition rule itself (`"no AI/ML language"`), not prohibited usage.

The trend warning renders as `"⚠ Sales increasing — Recent 3-day avg (X units/day) is higher than 7-day avg (Y units/day)"` — matching the required label from `calculation-rules.md` §4.

### FormulaTrace and FormulaDrawer coverage — confirmed

Dashboard table includes `FormulaTrace` on ADD_7, ADD_3, and ROP columns. The ADD_7 trace label reads `"ADD_7 = total sold in last 7 days ÷ 7"` with substituted values. The ROP trace shows the formula, the substituted values, and labels safety stock as "User-set assumption".

`FormulaDrawer` shows the full three-step derivation: Step 1 = ADD_7, Step 2 = target stock with "User-set assumption" tags on both `target_coverage_days` and `safety_stock`, Step 3 = max(0, ceil(target) − current stock) with the actual numbers.

Coverage column shows `"No recent sales"` when `stockCoverageDays === null` (confirmed in `DashboardPage.tsx` line: `stockCoverageDays === null ? 'No recent sales' : ...`).

### Frontend sales window boundary — consistent with backend

`ProductDetailPage.tsx` filters the locally-fetched sales list using `new Date(s.sale_date).getTime() >= todayMs - 6 * msPerDay` for ADD_7 and `>= todayMs - 2 * msPerDay` for ADD_3. This mirrors the backend SQL `date('now', '-6 days')` and `date('now', '-2 days')` boundaries (both inclusive of today). The metrics on the product detail page will match the dashboard for the same product.

### Accessibility — confirmed

All form fields in `ProductForm.tsx` and `ProductDetailPage.tsx` have `<label htmlFor>` bindings. Dashboard and product detail tables have `<thead>` with `<th scope="col">` on every column. `StatusBadge` uses both a CSS class for colour and the text label for screen readers (`role="status"`). `ConfirmDialog` uses `role="dialog"`, `aria-modal`, `aria-labelledby`, and closes on Escape. Focus management inside the dialog prevents keyboard focus from escaping.

### Test coverage — backend

43 tests across two suites. Formula suite: 36 tests covering normal, zero, fractional, and boundary cases for all eight functions. Sales route suite: 7 integration tests covering the five required scenarios (sale decrements stock, negative-stock rejection, upsert delta adjustment, negative delta on reduction, restock increments, restock movement type/sign, movements endpoint content and signs). The `calcTrendWarning(1, 0)` edge case is covered here.

### Test coverage — frontend

34 Vitest tests across seven formula describe blocks. Coverage mirrors the backend suite with one gap: the frontend does not test `calcTrendWarning` when `add7=0` and `add3>0`. This case is handled correctly by the implementation (returns `true` since `any positive > 0 * 1.20 = 0`), but the test is missing.
